# 0.8.0 Product Review Findings

A full-plugin review conducted as incoming product owner: every command, agent, skill file, reference file, asset, and script, plus the docs about the plugin.
Findings are ranked by user impact and effort, per the rubric in `../../skills/docs-assist/reference/audit-methodology.md`.
Each finding notes whether it shipped in 0.8.0 or remains a recommendation.

## Summary

The plugin is structurally healthy: single-sourced content types, a working config-resolution chain, real dogfooding, and CI that enforces its own rules.
The highest-impact problems were conceptual, not mechanical.
The plugin implicitly assumed a team rollout in paths that should be audience-neutral, duplicated its core intake loop in three places, and carried a stale cross-reference web in the frontmatter spec.
It also wrote directly to whatever branch the user happened to be on, which conflicts with the docs-as-code workflow it teaches.

## Tier 1: High Impact (Shipped in 0.8.0)

### 1. The Plugin Assumed a Team When It Should Calibrate

The design intent is one plugin serving two situations through the same workflows: a solo maintainer writing docs for their own project, and a docs lead rolling out standards across contributors.
The distinction should surface during discovery, and a cold invocation should default to a solo writer working with the rigor of a full documentation team.

What the review found:

- No workflow asked about contributor context, and nothing defined the cold-start default.
- Team framing leaked into audience-neutral paths: `commands/init.md` framed config as matching "the team's house style", `SKILL.md` offered `/docs-assist:init` "when a team would benefit", and the README presented committed config as a team-only feature.
- A solo maintainer reading those paths could reasonably conclude the config system was not for them, when they are the users who benefit most: their committed config is what lets the plugin act as their consistency-checking second reader.

**Shipped:** a "Calibrate to the Contributor's Context" section in `SKILL.md` that folds one context question into existing discovery moments (never a mode switch or a flag), defines the cold-invocation default (solo writer, full-team rigor, with the docs set's own internal consistency as the standard when no config exists), and reframes `init`, `audit`, and the README so committed config reads as valuable at every team size.

### 2. The Intake Loop Existed in Three Places

`reference/intake.md` is the canonical method.
`SKILL.md` summarizes it, which a router should.
But `commands/draft.md` restated moves one through five nearly verbatim, including the same block-quoted dump invitation, roughly fifty duplicated lines.
This is the plugin's own Maintenance Nightmare antipattern: the 0.7.0 rebuild already had to change the same wording in multiple files, and the next change would too.

**Shipped:** `draft.md` now defers the shared moves to `intake.md` and keeps only what is draft-specific: code verification, shaping, the outline checkpoint, drafting, refining, and finalizing.

### 3. The Frontmatter Spec Referenced Draft Steps That No Longer Exist

`reference/frontmatter-spec.md` mapped fields to `/draft` "step 7 (Finalize)", "step 4", "step 2", and "step 1".
The 0.7.0 rebuild made finalize step 11 and shape step 7, so every one of those pointers was wrong.
A reader cross-referencing the two files would be told the content type is determined during the shape step's old position, which is now the dig step.

**Shipped:** the spec now references steps by name (survey, dump, shape, finalize), which survives renumbering.
The same pass removed the duplicated example-safety rules from `reference/documentation-patterns.md` in favor of a pointer to the canonical `reference/code-examples.md`.

### 4. The Plugin Wrote Docs Straight to the User's Current Branch

`/docs-assist:draft` wrote files and `/docs-assist:update` edited the working tree with no branch discipline, while `reference/documentation-patterns.md` teaches "branch for changes, pull request review" as the docs-as-code workflow.
The plugin did not follow its own advice.

**Shipped:** a delivery convention in `SKILL.md`, applied in `draft.md` and `update.md`: in a git repo, offer to do multi-file docs work on a docs branch, and never commit to the default branch without being asked.
It stays an offer, not an ambush; the contributor's workflow wins.

### 5. Fan-Out Audits Never Received the Project Config

`commands/audit.md` fans large audits out across `doc-auditor` subagents, but nothing passed the resolved `.docs-assist/` conventions into the subagent brief, and the agent definition never mentioned project config.
Slices of a fan-out audit could flag style the project explicitly allows.

**Shipped:** the fan-out instruction now includes the resolved config in each subagent brief, and `agents/doc-auditor.md` reads `.docs-assist/config.yml` and `style.md` when present.

### 6. The Validator Skipped Docs Subdirectories

`scripts/validate.mjs` checked frontmatter only on files directly in `docs/`, so any doc in a subdirectory (including this report) escaped validation while CI's markdownlint glob (`docs/**/*.md`) still caught it.

**Shipped:** the docs frontmatter check now recurses.

### 7. Attribution Was One File Short of Airtight

The intent is that anyone may use, modify, and fork the plugin while attribution survives in all copies.
The `LICENSE` copyright line already names the author, but the repo had no `NOTICE` file, which is the Apache 2.0 mechanism (section 4d) that obligates redistributors to carry attribution forward.

**Shipped:** a root `NOTICE` file with the project name, copyright, and repository URL.

## Tier 2: Recommended, Not Implemented

These are real improvements that did not make this pass, in priority order.

### A Terminology Registry, the Example-Variables Pattern Applied to Words

`.docs-assist/example-variables.txt` keeps code placeholder values consistent, and the audit flags drift against it.
Product terms have the same drift problem ("workspace" vs "project", inconsistent casing of product names) and no registry.
A `terms` section in `style.md` already half-exists; the missing piece is the audit treating it the way it treats example variables.
This pairs directly with the solo-writer-with-team-rigor story and is the strongest candidate for 0.9.0.

### Release Notes as a First-Class Workflow

`reference/content-types.md` files changelogs under reference, and `/docs-assist:update` reads diffs, but no workflow turns a release's worth of changes into release notes.
The pieces exist: the diff summary from `update`, the intake loop for the why, and a Good Docs template (`release-notes`) already in the catalog.

### Consolidate the Audit Command and the Audit Methodology

`commands/audit.md` (166 lines) and `reference/audit-methodology.md` (68 lines) overlap on inventory, the analysis dimensions, and prioritization.
The command must stand alone when invoked directly, so this needs care rather than a mechanical merge; the likely shape is the command owning process and output format while the methodology owns the evaluation framework.

### Tidy the Tone-and-Voice Reference

`reference/tone-and-voice.md` carries a fragment that reads as leftover notes (the bare MD022/MD032 citation) and a two-link "Terminology Consistency" section with no guidance.
Fold the markdownlint citations into the rules they support and either grow the terminology section or point it at `style-guides.md`.

### Sharpen the llms.txt Section Naming

The "Optional" section groups the audit, impact-analysis, IA, and style-guide references, but they are not optional so much as lead-facing.
Rename to say who they serve.

## What Did Not Need Changing

Findings of health, recorded so the next reviewer does not re-litigate them:

- The content-type single-sourcing holds: every file points at `content-types.md` and none redefines the list.
- The config-resolution chain (defaults, inferred conventions, committed config) is coherent and correctly described in both directions.
- The subagent isolation design (`doc-intake`, `doc-recon` keeping piles and codebases out of the main conversation) is the right architecture and needs no rework.
- The template system's suggest-free-fetch-on-yes consent model is consistent across all five files that describe it.
- Reference-file token weight is proportionate: the largest file (`frontmatter-spec.md`, 201 lines) earns its length, and the skill loads references on demand rather than up front.
