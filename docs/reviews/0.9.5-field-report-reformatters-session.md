# 0.9.5 Field Report: dynamical.org reformatters Session

Field notes from using docs-assist 0.9.5 (the published marketplace version) end-to-end on a real repository (`dynamical-org/reformatters`, a Python weather-data project) over one long session: `/docs-assist:init`, `/docs-assist:audit`, `/docs-assist:plan`, `/docs-assist:health`, and finally `/docs-assist:setup-lint`. This is a usage report, not a code audit of the plugin's files: it's what the workflow felt like and cost from inside a real session, written for whoever picks up the next release.

Some of what follows may already be addressed in the in-progress next version. The working copy already references `reference.yml`, `docs-decay.mjs`, and `/docs-assist:verify`, none of which existed in the cached 0.9.5 this session ran against. Noted inline where a finding looks like it might already be fixed; the rest held up against the current working copy too.

**Headline finding:** the single biggest cost driver in this session was mechanical markdown checking done by hand, reading files, writing throwaway Python scripts to detect missing blank lines and untagged code fences, iterating, and missing things, across four separate incomplete passes, before the user had to explicitly redirect to "wouldn't it be easier to run vale and md check?" One `markdownlint-cli2` invocation then surfaced in seconds what those four passes spent many turns approximating and still didn't fully catch (a nested-fence bug that silently broke a chunk of a file's rendering). The plugin already says the right thing ("leave mechanical checks to linters") but doesn't act on it.

## Tier 1: High Impact

### 1. "Leave mechanical checks to linters" is a stated principle, not an operation

`commands/audit.md` says outright: "Leave mechanical checks to linters (Vale, markdownlint, cspell)." `commands/health.md`'s Consistency dimension is pure prose judgment ("do the docs agree with each other? Spot-check...") with no linter invocation. Compare this to the same file's link-checking step, which is fully operationalized: "Use the repo's own link-check setup if one exists... Otherwise, run `npx --yes markdown-link-check`."

Structural/prose checks don't get the same treatment. The result in this session: I spent the first several turns of "review the documentation" hand-writing Python to detect missing blank-lines-around-headings, untagged code fences, and broken anchors, reimplementing `MD022`, `MD032`, and `MD040` badly, one file at a time, missing several instances each pass (the user had to point out a second and third round of misses in the same file before I got it right). When I finally ran `markdownlint-cli2` for real, it found 607 issues in one command against the tool's own defaults, and 193 against a correctly-scoped config, including a genuine heading-level skip and several missing-blank-line instances in files I'd already "finished" checking by hand.

**Recommendation:** give `audit.md` and `health.md`'s mechanical-check language the same shape as the link-check step: if `.docs-assist/config.yml`'s `lint.tools` is configured, run the tools and fold their output into findings directly, as a first step, before any manual reading. If lint isn't configured yet, say so explicitly and offer `/docs-assist:setup-lint` before doing anything by hand; don't let "leave it to linters" be true in principle and false in the actual runbook.

### 2. `/docs-assist:setup-lint` scaffolds and stops; nothing runs the linter against a real baseline

The skill's process ends at step 6, "Show How to Run It," printing example `npx` commands. It doesn't run them, doesn't triage the first-run findings, and doesn't help the user decide which findings are real defects versus which reveal the generated config doesn't match the project's actual conventions yet.

In this session, after scaffolding, I had to separately: run `markdownlint-cli2`, discover 607 issues (mostly noise from `MD013`/`MD004` mismatches with the project's real conventions), diagnose *why* they were noise, hand-tune the config, rerun, triage the remaining 193 real issues file by file, fix them, and only then get to 0. That whole loop is exactly what a first-time setup needs and exactly what the skill doesn't walk through today.

**Recommendation:** extend `setup-lint.md` with a step 7: run the generated config against the target scope immediately, and walk the findings with the user. Fix what's real, adjust the generated config for what's a false positive against a documented `config.yml` field, and flag anything that's neither (a rule with no corresponding project convention at all; see finding 4) as a candidate to disable outright rather than something for the user to keep re-triaging.

### 3. Vale doesn't reliably resolve through `npx` for the recommended package

The setup instructions point at Vale as a standalone binary with no specific npm-installable recommendation in what I found; I chose `@vvago/vale` (a maintained wrapper that downloads the platform binary via postinstall). `npx --yes @vvago/vale --version` and `npx --yes --package=@vvago/vale -- vale --version` both failed with `vale: command not found`, even though the binary was correctly downloaded to `node_modules/@vvago/vale/bin/vale` (confirmed as a real, working Mach-O binary when called by direct path). This looks like an `npx` bin-resolution quirk with this package's `bin` field, not a broken download.

The workaround (`npm install @vvago/vale --no-save` into a scratch directory, then call `<scratch-dir>/node_modules/@vvago/vale/bin/vale` directly) cost several tool calls of trial and error to discover, and had to be documented by hand in the project's own `.docs-assist/config.yml` so it wouldn't be re-discovered next time.

**Recommendation:** either test and recommend a specific npm-installable Vale wrapper known to resolve cleanly through plain `npx`, or have `setup-lint.md` detect this exact failure mode (`npx` exits 127 with `command not found` despite a successful install) and hand back the direct-binary-path workaround automatically instead of leaving the agent to rediscover it. Given the CHANGELOG's Unreleased entry about moving prose checks onto managed upstream Vale packages (`Google`, `write-good`, `alex`), this is a good moment to also pin down exactly how those packages get installed and invoked in a real session, not just referenced by name.

### 4. `markdownlint`'s shipped template inherits the full rule catalog via `"default": true`, including rules with no corresponding project convention

`assets/lint/markdownlint/.markdownlint.jsonc` sets `"default": true` and then overrides only the rules `.docs-assist/config.yml` has an opinion about (`MD004`, `MD029`, heading/list spacing, fenced-code-language, etc.). Every other markdownlint rule runs at its stock default, including several with no config.yml field at all: `MD060` (table pipe spacing) produced 40 findings on tables that render identically either way, and `MD048` (fence-style consistency) actively flagged a fence-nesting technique the plugin itself would presumably endorse (an outer `~~~` fence wrapping an inner `` ``` `` fence, the only way to nest fenced code inside fenced "terminal output" without the inner fence prematurely closing the outer one, per CommonMark's rule that a closing fence can't carry an info string).

I ended up disabling both by hand, with a comment explaining why, in the project's `.markdownlint.jsonc`.

**Recommendation:** either curate the shipped template as an explicit allowlist of rules that map to a `config.yml` field (turning `"default": false` and only enabling what's configured), or ship the current noisy rules pre-disabled with the same reasoning comment I had to write myself, so a fresh `setup-lint` run doesn't reproduce this exact investigation.

### 5. `/docs-assist:init`'s convention detection can't distinguish real house style from prior-AI-generated habit

`init.md`'s "Detect Existing Conventions" step surveys the corpus and treats what it finds as the project's real style. In this session, that survey found heavy em-dash usage across the existing docs and (correctly, given only that evidence) offered it as the em-dash policy default. It later turned out the existing docs had been substantially written in a prior Claude-assisted session, and the em-dash usage was a model habit, not a decision anyone had actually made. Discovering this cost a full corpus rewrite later in the same overall engagement (~240 em dashes across 15 files) that a single calibration question during `init` could likely have avoided.

**Recommendation:** add one question to `init.md`'s detection step: whether the existing docs were written by a human, by AI assistance, or a mix, and if AI-influenced, treat detected stylistic patterns (not structural ones like heading hierarchy or file layout) as provisional rather than as confirmed intent. Surface them as "here's what I found; was this a deliberate choice?" rather than folding them straight into the proposed config.

## Tier 2: Recommended

### `MD029`'s shipped default (`"one"`) is stricter than most real corpora need

Even before finding 4's broader "unopinionated rules" issue, `MD029` specifically defaulted to strict repeated-`1.` numbering in the shipped template, while this project's docs defensibly mixed repeated-one and true sequential numbering across different files (both are legitimate; markdownlint's own default for this rule is the permissive `one_or_ordered`, which accepts either as long as a single list is internally consistent). The template overrides markdownlint's own sensible default down to the stricter option. I had to override it back. Unless `init.md` actually verifies that a project's ordered lists are already consistently one style before locking `ordered_list_style` in as an enforced rule (as opposed to just asking the user's stated preference), the generated config should probably default to `one_or_ordered` too.

### Fan-out thresholds are qualitative, and I never self-triggered one

`audit.md` says "for large documentation sets, fan out" without a concrete threshold. This session touched 12+ files across several thousand lines of changes in one continuous main-thread conversation and never fanned any of it out to subagents, despite the audit skill explicitly recommending it "for large documentation sets." A vague qualitative trigger is easy for an agent to talk itself out of applying turn by turn, especially once already deep in a session. A concrete number (file count, total line count, or estimated token cost) would make this a checkable condition instead of a judgment call that quietly never fires.

### No lightweight "session log" convention distinct from a docs content plan

`/docs-assist:plan` produces `docs/plan.md`, a forward-looking content plan. Over this session I improvised a running narrative log in that same file (plan items, execution notes, "what I found and why I made this call") because there was nowhere else that fit. It grew to several hundred lines mixing planning content with after-the-fact commentary. That's not really what `plan.md` is for, and there's no other docs-assist artifact designed to hold it. A lightweight, append-only session-log convention (separate from the content plan, not meant to be polished prose) might give agents a proper place for this instead of it leaking into whichever file happens to be open.

### Several sequential confirmation points could likely collapse into fewer round trips

Across `init` → `audit` → `plan` → `health` → `setup-lint`, I asked the user to confirm or choose at several separate points: the proposed `config.yml` values, whether to enable templates/lint/seed files, buy-in on the plan's scope, whether to continue past "ship now" into the next stage, and (implicitly, via the user needing to redirect me) whether to use real linters at all. Each individual question is reasonable in isolation and matches the "don't act without buy-in" design intent, but stacked across one continuous engagement they added up to a lot of back-and-forth for what the user experienced as one task. Worth a pass over the command set asking which of these could be batched into a single up-front question (e.g., one combined "here's what I'm about to do across the next several steps, confirm or adjust" moment) rather than one round trip per step boundary.

## What Worked Well

Worth naming, since a report this focused on friction can read as harsher than the experience actually was:

- The `config.yml` → generated-linter pipeline is correctly designed and, once actually invoked, worked exactly as documented: real project decisions (list marker, heading case, em-dash policy) flowed straight through to enforceable rules with no manual translation needed.
- `init`'s conversational calibration questions (heading case, em dash, prose line style) were well-targeted and each came with real evidence from the corpus rather than a blind default. The em-dash miss (finding 5) was a gap in what evidence was trusted, not in how the question was asked.
- The plan/audit/health command separation gave a clean paper trail across a long, multi-session-feeling engagement; it was always possible to tell what stage of work was happening and why.
- `/docs-assist:audit`'s explicit fan-out guidance and per-subagent config-passing (already fixed per the 0.8.0 findings doc) is the right shape; it just needs a size threshold to actually fire (Tier 2).

## Recommended Kickoff Prompt for a New Repo

Everything above is plugin-side. Until findings 1 through 5 ship, a user can route around most of the same friction from the user side, with a better first prompt. This section is written for that user: something to copy, adapt, and paste as the opening message in a fresh Claude Code session, in any unrelated repo, before running any `/docs-assist` command.

```text
Do a comprehensive documentation pass on this repo using the docs-assist
plugin. Before you touch any docs content:

1. Run /docs-assist:init first. When you survey the existing docs for
   conventions, tell me explicitly which ones look like real prose
   decisions versus what might just be a prior AI session's writing
   habit (em dash usage and list style are common cases). Flag anything
   in the second category as provisional and confirm it with me instead
   of locking it into config.yml.
2. Immediately after init, run /docs-assist:setup-lint for markdownlint
   and Vale, then actually run the generated linters against the repo
   right away, not just scaffold the config. Fix every real finding or
   tell me explicitly why a rule doesn't apply here (and disable it with
   a comment saying why), before moving on to anything else. From this
   point on, treat "run the linters" as the first step of any audit,
   health check, or review, not something to approximate by reading
   files by hand.
3. Then run /docs-assist:audit (or /docs-assist:health for a faster
   first look) and /docs-assist:plan. Propose one full plan up front,
   covering scope, priority order, and stages, and ask me to confirm it
   once. After I approve it, execute through to completion without
   pausing to ask permission at each stage boundary, unless you hit
   something genuinely ambiguous, destructive, or outside the plan's
   scope.
4. If any stage touches more than about five files or a few thousand
   lines total, fan the work out across subagents by file or logical
   group instead of doing it all in one long conversation.
5. Keep a running session log of what you changed and why as you go,
   separate from any docs/plan.md content plan, so I can review the full
   history in one place at the end.
6. Before you tell me you're done, re-run the linters one final time and
   confirm zero issues, or list exactly what's left and why you chose
   not to fix it.
```

A few notes on why each part is there, tied back to the findings above:

- Steps 1 and 2 exist because of findings 5 and 1: without them, the agent will treat whatever prose habits it finds in the existing docs as intent, and will default to hand-checking formatting instead of running the tools that already exist for it.
- Step 3 is a direct answer to the Tier 2 confirmation-fatigue finding: one plan, one approval, then a straight run instead of a round trip per command boundary.
- Step 4 gives the qualitative "fan out for large sets" guidance in `audit.md` a number to check itself against, since nothing in the plugin does that automatically yet.
- Step 5 fills the gap the Tier 2 "no session log convention" finding describes: asking for it explicitly gets the same benefit today, without waiting on the plugin to define the artifact.
- Step 6 catches drift between "the linters were clean when I set them up" and "the linters are clean now that the docs actually changed."

## Update: A Shorter Prompt, Now That the Findings Are Fixed

Findings 1 through 5 and the Tier 2 items above are now built into the plugin itself (`audit.md`, `health.md`, `setup-lint.md`, `init.md`, `plan.md`, `update.md`, `draft.md`, the shipped markdownlint template, and `SKILL.md`'s cross-command guidance), not something a contributor needs to ask for in the opening message. The kickoff prompt above is kept for the record; this is what should be enough to get the same result on a fresh repo:

```text
Improve the documentation in this repo.
```

That single line should now be enough to get a health check first, routing into whichever of init, audit, plan, and setup-lint the scorecard calls for, one batched confirmation instead of one per stage, linters run before any manual mechanical checking, a session log if the pass runs long, and a clean re-lint before it calls itself done.

If it doesn't land that way on a real repo, that's the next finding: note exactly where it diverged (which step got skipped, which confirmation still happened piecemeal, which mechanical check got hand-rolled) and it becomes the next fix, the same way this report's findings did.

## Update: The Shorter Prompt Found a Real Gap

Running the prompt above surfaced exactly that kind of next finding. The pass came back with the mechanical and structural work done (lint clean, headings and links fixed) and stopped there. It took an explicit follow-up to get the actual high-value work:

> those are nice cosmetic fixes that are worth doing. did you also do a component-based review that follows each claim or resource from the documentation into the codebase to see if there's information that's wrong, missing, could use an update, or that you could verify?

That question named the gap precisely: the plugin had strong machinery for verifying *procedural* steps (`/docs-assist:verify` executes them) and registry-tracked `fact` values (`reference.yml`'s `source` field), but nothing made a general claim-by-claim trace, every flag, config key, default, endpoint, and described behavior in the prose, out to the code, a mandatory part of a routine "improve the docs" pass. Audit's own "Accuracy" dimension was just "check version references and dates," vague enough that a lint-driven pass walked right past it. Findings 1 through 5 above fixed the mechanical-check gap; they didn't touch this one, and a lint-clean docs set that nobody re-checked against the code is not actually improved, just tidier.

Fixed by adding `reference/claim-verification.md` (what counts as a claim, how to trace one to source, and how to classify what you find: matches, drifted, missing, or needs `/docs-assist:verify`), and making it mandatory rather than optional in `audit.md`'s Content Issues step and `audit-methodology.md`'s Accuracy dimension. `health.md`'s Freshness dimension now says explicitly that the decay detector ranks which docs deserve this trace; it does not perform one, so a "solid" freshness rating no longer reads as "every claim checked." `SKILL.md`'s routing for a vague "improve the docs" request now says outright that a clean `setup-lint` and `health` scorecard are not the same as a genuine improvement pass, and names the claim trace as part of what a full audit means before the work starts, not as a surprise the contributor has to ask for.

The lesson generalizes beyond this one fix: a prompt that gets shorter because the plugin absorbed more of the checklist is only a win if the checklist it absorbed was the right one. "Improve the docs" getting easy to say is not the goal; getting easy to say *and* still reaching the claim-to-code work by default is.
